# テスト駆動開発とテストリスト

このコースでは，すべての機能をテストから書く．
この文書では，テスト駆動開発(TDD)の進め方，テストリストの書き方，単体テストと統合テストの分け方，テストの実行方法を説明する．

## Red → Green → Refactor

1つの振る舞いを，次の3つの段階で作る．

1. Red: まだない振る舞いを確かめるテストを1つ書き，実行して失敗することを見る．コンパイルエラーも失敗の1つである．失敗を見ることで，テストが本当にその振る舞いを確かめていると分かる．
2. Green: テストが通る最小のコードを書く．定数を返すだけの「仮実装」でもよい．次のテストが，仮実装を本物の実装へ押し出す．
3. Refactor: テストが通ったまま，重複を除き，名前を直し，構造を整える．

1回の繰り返しは数分で終わる大きさにする．
大きすぎると感じたら，テストリストの項目を分ける．

## テストリスト

テストリストは，これから確かめる振る舞いを箇条書きにしたものである．
各Iterationの`TESTLIST.md`に書く．

次のように書く．

- 要求と使用例を読み，「この入力のとき，こうなる」という形で1項目ずつ書く．
- 単純な場合から並べる．例えば「空の文書」「1行」「複数行」「誤りを含む行」の順にする．
- 境界を探す．空の入力，末尾の改行，先頭と末尾の空白，0での割り算などである．
- 既にあるテストの期待値が変わる場合は，「〜の期待値を…に変える」という項目にする．
- 実装しながら思いついた項目は，その場でリストに足す．終わった項目には`[x]`を付ける．

単語を数える関数なら，テストリストは次のようになる．

```markdown
## 単体テスト

- [x] 空の文字列は0語
- [x] "hello"は1語
- [x] "hello world"は2語
- [ ] 連続した空白は1つの区切りとみなす
- [ ] 先頭と末尾の空白は数えない

## 統合テスト

- [ ] コマンドに"a b c"を渡すと"3"を出力する
```

## 単体テストと統合テスト

| 種類 | 確かめること | 置き場所 |
| --- | --- | --- |
| 単体テスト | 1つのモジュールの関数を，入力と出力の対応で確かめる．LSPのメッセージは使わない | `test/unit/` |
| 統合テスト | サーバを起動し，エディタの代わりにLSPのメッセージを送って，応答と通知を確かめる | `test/integration/` |

振る舞いの細かい場合分けは単体テストで確かめる．
統合テストは「LSPのメッセージから，その機能に届き，結果がメッセージとして返る」ことを，代表的な1〜2例で確かめる．

テストのファイルは機能に属する．

- 単体テストは，モジュール1つにファイル1つで，`test/unit/Calc/ParserSpec.hs`のようにモジュール名にそろえる．
- 統合テストは，LSPの機能ごとに`test/integration/DiagnosticsSpec.hs`のように分ける．
- 機能を変えるIterationでは，そのファイルにテストを足すか，期待値を書き換える．Iterationの名前をファイル名には使わない．

## テストの書き方(hspec)

テストはhspecで書く．
`Spec.hs`はhspec-discoverの入口で，同じディレクトリの下にある`〜Spec.hs`をすべて集めて実行する．
各ファイルは`spec :: Spec`を定義する．

```haskell
module WordsSpec (spec) where

import Test.Hspec
import Words (countWords)

spec :: Spec
spec = describe "countWords" $ do
  it "counts no words in an empty string" $
    countWords "" `shouldBe` 0
  it "counts one word" $
    countWords "hello" `shouldBe` 1
```

## テストの実行

| すること | コマンド |
| --- | --- |
| パッケージのすべてのテスト | `cabal test <パッケージ>` |
| 単体テストだけ | `cabal test <パッケージ>:test:unit` |
| 統合テストだけ | `cabal test <パッケージ>:test:integration` |
| 名前で絞り込む | `cabal test <パッケージ>:test:unit --test-options='--match "countWords"'` |
| 登録したすべてのパッケージ | `mise run test` |

失敗したテストは，期待値(expected)と実際の値(but got)を並べて表示する．
Redの段階では，この表示が「まだできていないこと」を示しているかを読む．
